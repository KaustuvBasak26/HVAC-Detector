Automated HVAC Duct Detection and Annotation Web Application 1. HLD Objective This HLD defines the architecture of a browser-based application that allows a user to: 1. upload an HVAC mechanical drawing PDF  2. submit it for processing  3. detect ductwork and associated labels  4. measure duct lengths  5. preview annotated results in the browser  6. download annotated PNG/PDF and structured output  The sample drawing indicates a single-sheet mechanical floor plan, labeled M2.0, for DHC Midlothian, with a visible scale and plan layout. That supports a workflow centered on document upload, backend analysis, and annotated drawing generation.   2. Architectural Goals The architecture should optimize for: • web usability: simple browser-based upload and review  • asynchronous processing: drawing analysis may take time  • modularity: PDF parsing, duct detection, measurement, and annotation should be separable  • scalability: multiple jobs/users should be supported  • reviewability: the primary output is a visual markup  • traceability: jobs, outputs, and logs should be retrievable  • extensibility: future support for other MEP elements

3. High-Level Architecture Overview The system is composed of six primary layers: 1. Frontend Web App  2. API Gateway / Backend Application  3. Job Queue and Worker Layer  4. Document Processing Engine  5. Storage Layer  6. Observability and Admin Layer  The frontend handles user interaction. The backend handles authentication, job creation, metadata, and result serving. The worker layer performs long-running analysis. The processing engine performs the HVAC-specific logic. Storage persists files, results, and metadata. Observability supports debugging and operations.  4. High-Level System Context Diagram Explanation At the highest level, the user interacts only with the web app. The web app talks to backend APIs. The backend stores files, creates processing jobs, and delegates analysis to workers. The workers use the processing engine to generate outputs, which are then made available to the user. 15. Key Architectural Decisions 15.1 Why async job processing Drawing analysis is CPU-heavy and sometimes memory-heavy. Keeping it outside the request-response cycle avoids timeouts and makes UX better. 15.2 Why object storage Annotated PNG/PDF files and intermediate images are large binary assets and should not live in relational tables. 15.3 Why modular processing engine Future improvements may replace only one module, such as: • duct detector  • OCR/text extractor  • scale calibrator  • annotation renderer  without rewriting the whole app. 15.4 Why separate metadata and file storage This keeps the system scalable and operationally clean.

16. Recommended Tech Stack at HLD Level A good web-app stack for this design would be: • Frontend: React or Next.js  • Backend API: FastAPI or Node.js/NestJS  • Workers: Python workers  • Queue: Redis + Celery / RQ, or RabbitMQ / SQS  • PDF & vision engine: Python  • DB: PostgreSQL  • Object storage: S3-compatible storage  • Monitoring: Prometheus/Grafana or cloud-native monitoring  • Deployment: Docker + Kubernetes or ECS  Python is especially strong here because the core document-analysis pipeline depends on PDF and CV libraries.  17. End-to-End HLD Summary In one sentence: This system is a web application with asynchronous document-analysis workers that ingest HVAC mechanical drawing PDFs, isolate the plan area, extract text and duct geometry, associate dimensions and lengths, render annotated overlays, store outputs, and return previewable downloadable results to the user.
